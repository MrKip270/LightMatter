About LightMatter

What can you actually see in the sky tonight?

LightMatter is a free, ad-free stargazing app that turns scattered astronomy data into one plain-language answer. It combines a live cloud cover forecast, a light pollution map built from satellite sky-brightness data, moon phase and moonlight-brightness modeling, and aurora borealis probability from NOAA space-weather data into a single viewing score and a best-time-to-go-outside window for any location on Earth. It’s built for casual sky-watchers, astrophotographers planning a shoot, aurora chasers deciding whether to drive, and anyone who wants a dark sky finder to locate the nearest low-light-pollution site near them — a night-sky visibility and astronomy planning tool, not a telescope or equipment store.

The story

Why I built this

I’m a CS student, and LightMatter started as a way to actually learn full-stack development rather than follow a tutorial — a real problem, end to end: a backend that talks to live APIs, a frontend with no framework to hide the DOM from me, real automated tests, and enough surface area (astronomy, geography, projections, race conditions) to keep it interesting past the first weekend.

The actual itch was simpler: checking whether tonight is worth going outside means checking a cloud forecast, a light-pollution map, a moon calendar and an aurora dashboard separately, then combining them in my head. LightMatter exists to do that combining for you — and to teach me, one data source at a time, everything from HTTP fan-out and partial failure handling to bilinear interpolation and why magnitudes can’t be averaged like normal numbers.

Under the hood

Tech stack & architecture

Backend is Node.js + Express; frontend is plain HTML, CSS and JavaScript — deliberately no framework and no build step, so every line in the browser is a line I wrote and can explain. The map is Leaflet over OpenStreetMap tiles. PostgreSQL is installed for when the project has genuinely relational data (saved locations); the light-pollution grid turned out to be a fixed raster, so it lives in memory instead.

  • Sources vs. routes. Data logic (backend/sources/) is separate from HTTP wrappers (backend/routes/), so the combined /api/sky endpoint calls every source directly as a function instead of making a route call another route over HTTP.
  • Independent degradation. The combined report uses Promise.allSettled, not Promise.all — one upstream API being down degrades its own section instead of failing the whole response.
  • Server-rendered map tiles. The light-pollution and aurora overlays are rendered as PNG map tiles on the backend, not a single stretched image — the source grids are in plain latitude/ longitude (EPSG:4326) and Leaflet renders in Web Mercator (EPSG:3857), so a naive overlay would misplace high-latitude dark-sky sites by hundreds of kilometres.
  • 226 automated tests, Node’s built-in test runner, no dependencies — including property-based tests that sweep a whole domain (every hour of the lunar cycle, every latitude band) rather than a handful of hand-picked examples.

What I learned

Lessons learned

These aren’t hypothetical — each one shipped a real bug before it became a rule I follow now.

  • Combine brightness in linear flux, never in magnitudes. Magnitudes are logarithmic, so averaging them computes a geometric mean, not the answer you want. This caught three separate bugs: downsampling the light-pollution atlas, adding moonlight to skyglow, and averaging sky brightness across a night.
  • null <= 20 is true in JavaScript. null coerces to 0. Without an explicit null check, a gap in cloud data silently reads as a perfectly clear sky.
  • Timestamps aren’t automatically instants. One API returns naive local-time strings scoped to the searched location, not the server or the viewer. Passing one straight into new Date() re-anchors it to the wrong timezone — invisible in development, wrong in production.
  • Leaflet reports unwrapped longitude. Panning east gives you 190°, 550°, 910° — all rejected by a ±180° API. Every map click gets normalized before it’s sent anywhere.
  • Library versions change units without warning. The moon-position library returns degrees in the version this project uses; most tutorials online still assume the older version’s radians. Verified empirically rather than assumed.
  • A raster in one projection isn’t a raster in another. The light-pollution grid is equirectangular; the map is Web Mercator. Treating them as interchangeable would have quietly misplaced every dark-sky recommendation near the poles.

What’s next

Future improvements

Roughly in the order I plan to tackle them:

  • Severe weather alerts — a tornado or storm warning should be able to override the score entirely; a warning isn’t a stargazing condition, however clear and dark the sky is.
  • Naked-eye planet visibility — replacing a static "bright planets" threshold with a real ephemeris so the report can say "Jupiter, southeast, 40° up" instead of a generic maybe.
  • Satellite and ISS passes — the first feature that will need an API key, which also means finally wiring up proper secrets handling.
  • A land/water check for the dark-site search — right now a coastal or island search can recommend a point out in open ocean, since unlit water clears the darkness threshold trivially.
  • Newer, higher-resolution light-pollution data — the current atlas is from 2015, so real skies are somewhat brighter than reported; a newer dataset and a finer grid are both on the list.
  • Saved and compared locations — the first genuinely relational data in the project, and the reason PostgreSQL is already installed and waiting.
  • An actual deployment — everything above is running on my machine for now.

Credits

Data sources

LightMatter doesn’t collect or measure anything itself — it fans out to the sources below and combines what they return. Full credit to the people and agencies who make this data public:

  • World Atlas of Artificial Night Sky Brightness — Falchi, F. et al. (2016), GFZ Data Services, doi:10.5880/GFZ.1.4.2016.001. Licensed CC BY-NC 4.0 — see the licensing note below.
  • NOAA Space Weather Prediction Center — aurora (OVATION) probability and forecast timing.
  • Open-Meteo — place-name geocoding and hourly cloud cover / sunrise / sunset forecasts.
  • OpenStreetMap — Nominatim reverse geocoding, and the basemap tiles rendered via Leaflet. © OpenStreetMap contributors.
  • NASA/GSFC Five Millennium Canon of Lunar Eclipses — verified eclipse timing.
  • suncalc — moon phase, illumination, altitude and rise/set, computed locally from Meeus’ Astronomical Algorithms, no network call required.
